Overview and principles

A patient checking for a Thursday opening and a coordinator untangling a double-booking need different densities, but they must never disagree about what “pending” looks like or which button commits a booking.

Without a shared foundation, the consumer app and the admin platform drift: two blues for “confirmed”, a status chip that relies on color alone, a 32px tap target that was fine with a mouse. Each fix lands in one product and not the other. This system makes those decisions once, as named tokens, and lets each platform choose only what genuinely differs: size and density.

Clarity before decoration

Every color, size and weight has a stated job. If it doesn’t help someone find, book or manage an appointment, it doesn’t ship.

Semantic names describe role (color.text.secondary), never appearance.

Never color alone

Status meaning survives grayscale, color-blindness and a glance in sunlight.

Each status ships a label and icon; pending is dashed, cancelled is struck through.

Calm, then confident

Neutrals carry most of the interface so the one decisive action stands out.

Blue is reserved for action and selection; status hues stay on tinted fills.

One language, two densities

Patients get touch-first sizing; coordinators get data-dense layouts. The vocabulary is identical.

47 platform tokens share names; size.control.md is 48px on mobile, 36px on desktop.

Accessible by construction

Contrast is a build requirement, not a review comment.

The build fails if any audited pair drops below WCAG 2.2 AA.

Change in one place

A brand or accessibility decision updates every product surface without a hunt.

Components never reference primitive colors; the build enforces it.

Efficiency for operators

Coordinators scan hundreds of rows a day. Density and alignment serve speed.

40px table rows, tabular figures, 12px minimum in calendar events.

Shared or platform-specific?

The rule: if a patient and a coordinator should perceive the same meaning, the token is shared. If the difference comes from input method or information density, it is platform-specific.

Shared across platformsVaries by platform
All color: text, surface, action, status, feedbackControl heights and touch targets
Status labels and iconsText-style roles (body 16 vs 14)
Focus ring, stroke widthsCard, page and cell padding
Motion and easingRadius (12 vs 6 on controls)
Spacing rhythm (inline, stack)Grid columns, gutters, margins
Elevation, z-index layersTable row height, avatar size

Scoped re-resolution

CSS custom properties resolve where they’re declared, not where they’re used. If --cv-button-height-md were declared only on :root, a [data-platform="mobile"] subtree would inherit the desktop answer. The build re-declares base-semantic and component tokens on every [data-theme] and [data-platform] scope, which is why the hero demo can run a dark mobile phone next to a light desktop table on one page. A Playwright test checks this in Chromium.

/* generated/clearvisit.css */
:root, [data-theme], [data-platform] {
  --cv-button-height-md: var(--cv-size-control-md);
}
[data-platform="mobile"] {
  --cv-size-control-md: var(--cv-size-48);
}

Color

Seven hue families generated on one OKLCH lightness ladder. Because every 600 shares a lightness, “600 on white passes 4.5:1” is true for blue, green, red and violet alike, which made the semantic mapping predictable.

Typography

Atkinson Hyperlegible Next, designed by the Braille Institute for low-vision readers. In a product built on names, times and dates, distinguishable characters matter more than personality.

Aa Rr 10:30
Il1 0O 8B 5S, Dr. Ilona Ollis, room 101

Capital I, lowercase l and numeral 1 are all distinct; so are 0 and O. Mobile body text stays at 16px so iOS doesn’t zoom form fields on focus.

JSON and implementation

DTCG 2025.10 JSON is the source of truth. Everything else on this page is generated from it.

  3. ValidateTypes, aliases, cycles, layering, completeness and contrast across all 4 permutations.
  4. TransformCSS variables, Figma import files, resolved bundles, docs tables.

Governance

Tokens are a public API. Changing one is a release, not an edit.

ChangeExampleVersionRequired
New tokenAdd color.status.no-showMinorLight and dark values, label and icon, contrast pass, docs entry
Value change, same meaningcolor.action.primary.bg moves from blue 600 to 700MinorContrast re-run, before/after screenshots in both products
Primitive tuningAdjust the OKLCH ladderMinorFull contrast audit, every semantic consumer reviewed
Rename or removalfield.border-hover → field.border-interactiveMajor$deprecated for one minor cycle first, with a pointer to the replacement
New platform or themeHigh-contrast themeMajorComplete value set; the build rejects partial contexts

Deprecating a token

{
  "border-hover": {
    "$value": "{color.border.hover}",
    "$deprecated": "Use {field.border-interactive}. Removed in 2.0."
  }
}

Before a token change merges

The build passes: no unresolved aliases, no cycles, every theme and platform complete, every audited pair at WCAG AA.

The change is described in terms of meaning (“pending should read as waiting, not warning”), not just value.

Someone checked it in both products, in both themes, and with a color-blindness simulator for any status or feedback change.

Figma variables were re-imported from the generated files, not edited by hand.

ClearVisit is a conceptual portfolio project. Provider names, clinics, patients and figures are invented sample data. No usability testing or production use is implied.
